# 任务对齐与调度

## 角色

| 角色 | 负责事项 | 边界 |
| --- | --- | --- |
| 用户 | 确认范围与开始，裁定 findings，授权交付 | 决定当前修复、延期或接受风险 |
| 主协调者 | 对齐需求、拆分任务、调度、跟进、核对交接、汇总结论 | 不以派发任务代替完成任务，不将未验证项写成通过 |
| Coder | 范围内实现、自测、提供稳定快照 | 不自行扩大需求、提交、发布或清理无关内容 |
| Verifier | 对稳定快照独立验收、报告证据与问题 | 不修源代码，不直接给 Coder 追加任务或要求即时修复 |

## 开始前的任务契约

使用 [任务契约模板](templates/task-contract.md)，至少明确：

- 目标与关联需求；本次允许修改的文件或模块。
- 排除项、已知限制、待定项及其是否影响当前任务。
- 可观察的验收条件、检查方法、交付物和证据位置。
- 用户已经授权的操作，以及尚未授权的下一阶段。

用户明确“开始”“执行”等后推进对应开发任务。已经确认的子 agent 开发模式及本任务内的操作授权持续有效，不重复询问；这不等于提前授权后续任务、提交、发布、破坏性清理或额外目标实测。

常规实现细节由执行者在契约内处理。遇到需求冲突或需要改变技术边界时，保留已有结果，由主协调者汇总给用户；不借实现选择增加全局输入回退、注入等未授权能力。

## 调度规则

- 默认主协调者 + Coder 子 agent + 独立 Verifier 子 agent；各角色默认继承主会话模型与推理等级，单独调整前说明调整内容与原因。
- 同一源码范围同一时间只有一个写入者。拆分多个 Coder 前明确互不重叠的文件所有权及集成责任。
- 主协调者派发后持续跟进至完成或明确阻塞，消费 Coder 的问题和交接，不在派发后结束当前任务。
- 开发期间如开展预审，仅只读收集和排序候选问题；不打断 Coder，也不形成即时修复队列。
- Coder 提供稳定快照后，主协调者先核对契约、改动清单、自测结果、未执行项和快照可归属性，再准入正式 Verifier。
- 验收期间冻结被验源码；主协调者将 findings 一次性返回用户。未获用户处置前不自动启动修复。

## 任务记录

按需建立 `aiwork/workflow/runs/<task-id>/`，用同一任务编号关联：

- `task.md`：任务契约与用户确认摘要。
- `coder-handoff.md`：交接、快照标识及自测结果。
- `verifier-report.md`：独立验收及用户处置记录。

修复轮次在同一任务目录内编号并关联新快照，保留原 findings 和结论。调查细节放到 [debug](../debug/README.md)，任务记录引用即可；不复制整个源码或编译缓存作为日志。

持久记录采用仓库相对路径，命令注明执行目录；证据仅包含与任务相关的信息，并遵循 [脱敏约定](sanitization.md)。
