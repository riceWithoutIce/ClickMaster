# IPC主程序集成技术筛选

日期：2026-10-22。用户已同意主程序通道选择、IPC单次集成的分轮范围。采用technology-selection流程核定实现，不重新选择主产品框架。

## 基线与候选

基线为Tauri/Rust主程序的后台窗口消息单次任务；TapTapLoot两种消息均无玩法响应，独立C#管道测试单次/低频已获人工响应确认。协议与客户端身份依据见既有IPC分析及EXE任务，不重新读取游戏程序集或发送。

| 候选 | 支持与分发 | 生成数据与边界 | 代价及决定 |
| --- | --- | --- | --- |
| 保留窗口消息，不新增IPC | 现有依赖及便携EXE | 原目录不变 | 无法解决已确认游戏兼容问题；保留为默认通道 |
| Rust原生IPC，同EXE受控worker隔离阻塞读取确认 | 现有windows-sys 0.61.2缓存提供CreateNamedPipeW/GetNamedPipeClientProcessId及安全描述符API，现有Rust/Tauri构建路径 | 主程序负责倒计时/停止与所创建Child；worker只负责一次受核验传输，数据在EXE同级data，开发产物在build | 需移植身份/传输/监督并验证；批准本轮有限集成 |
| 打包C#测试器为产品sidecar | 已有测试证据，但依赖.NET Desktop Runtime及多文件 | 新增运行时和独立数据/进程边界 | 改变正式分发前提，不采用 |
| 在UI线程同步等待FlushFileBuffers | API可用 | 无进程隔离 | 会使停止/退出响应受阻，不采用 |

候选证据：仓库Cargo.toml、锁文件及本地windows-sys源码，项目环境入口和忽略规则，独立IPC-EXE稳定源码。未引入外部项目，未联网下载或安装。

## 入选方案门槛

| 门槛 | 结论 | 依据 |
| --- | --- | --- |
| Windows x64及目标API | pass | 现有Windows依赖本地缓存含原生命名管道/身份/ACL接口；实际编译仍为交付门槛 |
| 支持的构建及便携分发 | pass | 延续Rust/Tauri单EXE，同EXE worker不新增.NET依赖 |
| 生成物/缓存/临时目录 | pass | 沿用scripts/environment.mjs；worker启动前继承项目内或EXE同级data临时环境 |
| 忽略与隔离 | pass | build输出及所有data目录已ignore；旧测试器和回执保留 |
| 安全、隐私及副作用 | pass（设计边界） | 仅当前用户、本地、first-instance；绑定实例/版本/客户端验证；不全局输入、提权或注入；只结束直接拥有的Child |
| 可重复验证与移除 | pass | 项目内离线构建/纯回归；删去新模块及接线即可回到默认消息模式，不修改游戏 |
| 集成边界 | pass | 新IPC/通道模块与现有单次状态联动，启动不创建游戏管道，无隐式发送 |
| 相对基线收益 | pass | 用已人工确认的游戏通道补足PostMessage无响应目标，保留用户其他窗口操作方式 |

以上支持有限实现，不等于新Rust路径已验证。实现必须对worker入口做授权校验，并采用单调时间、连接/写/读取及总时限、停止后等待自有worker退出；不得将无法确认清理写成正常完成。若本地依赖不足或必须改变分发/禁止边界，停止相关实现并报告，不自行换技术。

验证只运行纯回归、构建及不查询/连接真实游戏的受控fixture；真实主程序游戏响应/停止/关闭/隔离由用户验收。任何fixture不得使用真实游戏管道名或游戏目标。无自动游戏实测、提交、推送、发布或清理旧证据。
