# IPC性能基线计划

状态：独立非游戏基线、最终实现路径A/B及等87帧比较均已完成，见baseline-report.md；完整产品与真实游戏仍未测。以rc.3冻结快照为功能基线；不把原任务fixture或截图当作代表性性能基线。

执行方式补充：用户选择独立非游戏接收器。允许自动构造随机私有管道、fixture进程/窗口并测量，不连接游戏固定管道或查询真实游戏身份；以明确区分的非游戏发送端/接收端口径报告，不冒充真实Tauri/WebView2/游戏完整基线。接收端负载单列，未运行UI因此WebView2记不适用，不能报告为完整产品0占用。

## 场景与口径

同一电脑/电源模式、同一包、同一目标及界面可见状态，比较待命、2000/2000毫秒、100/100毫秒三种场景。固定间隔排除随机等待的影响；100～110的原用户回执仍保留，不直接混作100/100基线。每个场景稳定后采样30秒，必要重复以判断波动；记录期间外部负载变化，不用单张任务管理器截图下结论。

分别统计主进程、自有短命worker、可归属的WebView2进程，报告分项及总和。以进程身份/创建时间及父子归属匹配，不能只凭名称把其他软件的WebView2计入；过快退出的worker若采样遗漏，需说明并补充生命周期计数或选择能捕获该成本的方法。

指标：整机口径CPU均值及波动、实际采样时长/逻辑处理器数、工作集/专用内存、worker创建次数、实际已发送次数与错误/结束原因。短周期数据不足以证明长期无增长，持续运行稳定性另列人工验收。

优化前后同时比较固定时间负载和每次完整写入的CPU开销。确保发送量和目标状态可比；吞吐下降、消息遗漏或误停不能算性能收益。不先承诺具体CPU百分比，取得基线后再冻结改进目标。

## 采集边界

只读采样不改变程序/游戏状态，不自动打开UI、建游戏管道、发输入、改频率/焦点、最小化或停止任务。用户主动控制实际场景；用户未准备场景时，可以先进行源码分析与非游戏测量设计，但不得标记真实基线完成。

尽量使用已有系统查询能力，不预设安装分析器或管理员级追踪。若需要新工具、性能跟踪或额外采集范围，先说明具体用途与输出边界。证据仅写 `build/verification/TASK-008-IPC-EFFICIENCY/`，环境按scripts/environment.mjs和generated-data约定；不保存真实路径/标题/命令行/令牌/PID清单。

## 第一阶段通过条件

待基线取得后补具体资源阈值。行为必需：IPC前后台均可发送，停止/限时及原实例保护保持；相同发送量下CPU成本下降，worker不重叠、不泄漏，失败原因可识别。静态/fixture、非游戏性能与真实游戏结果分别报告。
