# 第一阶段具体实现边界

状态：基线完成，协调者准入Coder实现。基线原始源已由独立性能agent冻结，不能重跑prepare覆盖；具体结果与限制见baseline-report.md。

- 快速检查：父端监督约10ms、轮间等待约50ms仍检查取消/限时、持有的原目标进程句柄、直接窗口PID/TID/可见/非最小化/客户区有效，不全局枚举、不检查前后台。
- 完整发送检查：实际worker唯一一次写入前保留全进程唯一实例、唯一Unity窗口与原实例身份核验，并核对实际管道客户端。该检查不放入读取观察循环。初始准入也保留必要完整核验。
- UI状态复用：普通查询按绑定epoch复用兼容结果；选择通道/开始任务强制核验，worker逐帧校验游戏程序集。缓存的UI可用状态不能直接授权发送，换绑失效。
- 授权和文件校验：本阶段保留逐帧父/子EXE哈希、游戏程序集哈希、一次授权、父进程实例/私有stdin源核验、DACL和first-instance。不采用仅path/mtime的哈希缓存。其剩余开销在交付说明中保留。
- 固定脱敏错误：保留首次实际失败阶段/原因及必要系统码；读取失败只诊断，不盖过写入结果。手动/限时/目标及清理错误保持正确优先级，无原始路径/PID/token/无限日志。
- 前台交互：专用IPC不因焦点改变停止，不激活游戏；非最小化要求保持。原消息通道不变。

资源验收在基线后填写：主要比较相同受控接收策略下的单位发送CPU及整机归一CPU、发送量、退出/泄漏；真实软件及游戏仍待人工。即使受控A/B改善，也不宣传为完整UI/真实游戏资源降幅；若效果不足如实交付并保留任务级worker为后续，不能自动扩大范围。

## 基线后的测量目标

已有非游戏100ms/2000ms场景分别87/14帧，每个30秒场景父端full校验896/525次，支持优先消除热循环全枚举。实现后父端full次数应移出10/50ms循环，逐帧写前完整核验仍存在。用同一fixture记录CPU均值/波动和每帧CPU，发送量不得下降来换CPU；如吞吐变化显著，增加等帧数对比。第一阶段目标是相同工作下发送端与worker合计CPU/帧降低，并呈现剩余worker/hash成本，不先宣传未经测量的降幅。功能、清理、保护优先；若测量不支持性能改善必须标记不足而非自动重构。
