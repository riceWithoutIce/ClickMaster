# TASK-011 技术筛选记录

本任务不引入新技术或依赖。候选是现有受控命名管道上的单 worker/持久连接生命周期调整，保留当前 Rust/Tauri/Windows 原生实现。

依据为现有 `ipc_runtime.rs`、`ipc_worker.rs`、`ipc_native.rs` 与 rc.6 日志，采用 technology-selection 规则评估。用户已明确同意连接复用并追加1ms测试边界，不重复请求既定范围授权。

| 候选 | 优势与成本 | 决定 |
| --- | --- | --- |
| 保留每帧worker/连接 | 无架构变更，但每帧约940ms建连仍存在 | 保留单次路径，重复路径需改善 |
| 一次运行复用受控worker/连接 | 减少进程启动/重复建连，需新增会话与逐帧监督 | 批准有界实现与隔离测试，真实兼容待验 |
| 仅复用worker、每帧断开重连 | 可减少进程启动，对主要连接等待帮助未知 | 延期，不作为不兼容时自动回退 |

本问题是现有原生传输生命周期的调整，没有必要引入第三方库候选。未下载、安装或升级任何依赖。

既有`build/verification/TAPTAPLOOT-IPC-CONSUMERS/result.json`的`TypingFarmerThread`静态IL显示：同一stream内循环ReadString，每次读取前Sleep(90ms)，一般异常后Sleep(1000ms)。该证据支持多帧复用假设，但不是本轮游戏运行验证；异常后等待与旧日志940ms接近，不能仅据接近断言全部延迟因果。1ms测试必须披露管道缓冲和客户端消费不同步，停止后不再写入不等于撤回已发帧；保持既定“读取仅诊断、不阻断发送”。

## 选择理由

- rc.6 日志将主要等待定位到每帧 `connect`：累计约 46.98 秒、平均约 940ms；写入累计约 0.216ms。
- 持久连接是减少重复建连的最小候选；先用项目内隔离接收器验证多帧协议，再进行真实目标人工验证。
- 1ms 只作为边界输入，不能绕过系统调度、管道往返和游戏处理能力。所有实际吞吐必须以测量值记录。

## 硬门槛

- 不改变 IPC 身份、授权、版本/程序集校验、目标实例核验、停止/退出语义。
- 不自动回退消息模式、全局输入、DLL、驱动或注入。
- 连接断开和目标失效必须停止并清理；不通过自动重试掩盖失败。
- UI 不得被连接等待同步阻塞；如无法在现有协议中复用连接，保留失败证据并返回重新对齐。
