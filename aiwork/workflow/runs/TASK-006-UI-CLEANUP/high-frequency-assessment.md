# 30/60次每秒可行性评估

日期：2026-10-22。状态：只读评估完成；未实施、运行POC、降低需求或发送。用户明确希望实际达到每秒约30或60次，先评估，困难时再讨论降低。

## 目标与证据范围

评估口径为独立数量1输入的持续完成/游戏响应频率，不是UI刷新率、配置等待值或放大单帧数量后的计数。30次/秒的完整周期预算约33.33ms，60次/秒约16.67ms。游戏FPS只是帧时间参考，既无帧同步接口，也不能证明IPC处理同频。

本轮仅阅读当前Rust源码及已保存游戏IL分析结果，无进程查询、安装目录重读、浏览器、游戏下载、内存操作或输入。游戏侧证据为`build/verification/TAPTAPLOOT-IPC-CONSUMERS/result.json`，对应程序集SHA256 `BC5318AC557E4039ADCCAE8D79EAF66F6C0200D18FC043FD2AA632F6513C35B8`。未刷新当前安装；结论针对该已核验版本，当前适配器亦锁定此hash。

## 确定的限制

1. 游戏`BongoCat.IPC.Ipc::TypingFarmerThread`在连接后检查循环条件，跳入每轮`Thread.Sleep(90)`，再调用`StreamString.ReadString`、解析并累加_taps。读取单个协议帧之前至少经过这段休眠；重新连接仍走同一逻辑。按当前串行单帧正确传输语义，接收上界约1000/90=11.11帧/秒，读/连接/解析耗时会继续降低，不能据此承诺实际稳定11次/秒。
2. 游戏主线程`Ipc.Update`将_taps聚合调用一次`GlobalKeyHook.Sim(_taps)`再清零；已保存消费链显示ClickCounter按数量加值，但TickClock每次事件只加一个tick，不按数量循环。因此“每帧传3/6个”可能提高计数值，不等价于独立30/60次输入或玩法推进。
3. 当前ClickMaster `ipc_runtime.rs`每帧启动同EXE受控worker，进行匿名授权、身份/版本核验、建管道、写、drain和退出，再等待设置间隔。监督传输sleep30ms，轮间等待sleep50ms，并经文件交换阶段状态。这些均增加周期/抖动；将最低等待2000改17ms不会成为60次/秒。持久worker/连接可减开销，但不能消除游戏90ms读取限制。
4. 消息通道目前50ms按下/释放配对，加上100ms最低额外等待，现实现亦不支持30/60完整对/秒。更改其时序可针对消息型目标另评估，但TapTapLoot的PostMessage键鼠已有人工失败，不能当本游戏的高频回退。
5. 当前rc.1还有单次IPC失败的人工反馈，具体原因未定位；既有低频通过不能代替该新包成功。此问题独立记录，不归咎于高频或参数2000/2001。

## 决策与后续

决策：**reject：通过现有TapTapLoot专用IPC实现独立30/60次每秒的方案**。保留用户30/60目标，不默默降为11次/秒或更低，也不承诺换为持久连接就能达到。

推荐先只读定位rc.1单次失败并改善可见诊断；若用户选择保留该IPC路线，再另行确认一个低于接收上界、需实测的频率目标和有界性能验证计划。若坚持30/60独立玩法事件，则需目标侧不同的受支持能力；当前证据没有这样的入口，不采用注入/驱动/全局输入绕过既有边界。

后续如获授权进行低频优化POC，应先冻结测试周期/总量、实际完成次数与分布、资源占用、停止/到期/身份失效、有界数据和桌面隔离指标，非游戏fixture先行，真实游戏由用户观察。当前不生成POC脚手架，不改已交付rc.1包或历史证据。
