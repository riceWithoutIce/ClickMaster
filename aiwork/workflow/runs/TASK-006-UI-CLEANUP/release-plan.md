## 同一任务内分阶段

1. 对齐并冻结本任务UI/首版范围、版本和交付方式后，用户授权开始开发。
2. Coder实施UI与确认后的发布辅助内容，自测并提供稳定源码/包快照；独立Verifier集中审核，findings交用户裁定。
3. 在build/staging准备候选并在项目内隔离副本验证，不在release槽位运行。用户对候选包进行人工体验、视觉与交互反馈；汇总到对应版本记录，明确当轮调整与延期内容。
4. 在授权范围内按反馈迭代为rc.2、rc.3等。每个交给用户的RC版本关联独立快照、包hash、变更说明和验收结果；已交付版本号不用于另一份不同包。验收后再改动须标明哪些证据仍适用，修复复审仅覆盖当轮改动和紧邻回归，不无故重开全面审核。
5. 不限定RC轮数，不因一次“验收通过”自动转正式版。体验/视觉/交互反馈已处理或明确延期、发布检查完成且无未处置阻塞项后，由用户明确确认进入0.1.0正式发布。
6. 具体产物和晋级清单可审阅后，按授权进入release/preview或current；版本转换若改变二进制，需为新产物建立证据，不能把rc包改名冒充正式版。提交/推送/远程上传由对应授权执行。

多轮RC不会增加发布槽位数量：release/preview仍只保留最新一个候选，替换前核对旧版本的记录和必要证据；历史版本的反馈、变更、hash及验收元数据保留。需要保留旧问题包时先安排现有槽位和受管理证据计划，不无限增加预览包或借build目录规避归档上限，不自动删除唯一问题证据。

沿用现有current1+archive2+preview1套上限，主要ZIP不重复保存完整解压副本；元数据长期保存。无自动历史清理，本任务不能删除TASK-005及旧IPC唯一证据。没有第二个平台或缺失Runtime环境时诚实保留NOT RUN，不伪造通过或为补证修改外部系统。
