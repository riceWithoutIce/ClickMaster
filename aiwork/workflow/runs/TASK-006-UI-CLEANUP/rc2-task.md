# rc.2：IPC读取确认不阻断发送

日期：2026-10-22。用户确认“可以记录是否成功，但是不应该阻断，我们继续”。授权本轮实现、非游戏自测、独立验收和本地rc.2便携候选；不操作真实游戏/正常UI、提交推送、正式发布或清理历史。

## 冻结行为

- IPC完整固定单帧写入成功即记为已发送一次。读取确认只是诊断：已确认、未确认或失败均不因该确认本身阻断下一轮；不重发同一帧，不把未确认显示为执行失败。
- 保留目标/客户端身份、版本、ACL、first-instance、固定数量1、单次授权与独立自有worker边界。连接/完整写入失败仍停止；按钮/F8/托盘/限时、目标失效与清理未确认保护保留。
- 读取结果不等于游戏玩法结果。界面/次数/说明统一采用“已发送”口径，诊断明确仅传输层读取确认；当前无游戏业务回执。仅本轮内存记录，不追加无限日志。
- 读取确认不再使用10秒等待作为每轮成功门槛。允许短时有界的后台收尾/诊断窗口（初始内部预算200毫秒，实际由受控fixture评估），不得无限等待、积累线程/worker或重叠发送。观察未确认后有界清理继续，不承诺未知接收端一定消费。
- 写入后即停止/到期也准确记录已发送次数，不能把清理异常伪装成功。保留明确结束原因，已发指令不能撤回。固定/随机间隔及最小2000毫秒不变，不混入高频优化。
- 核查并用受控fixture覆盖父端看到worker退出时的最终回执收集，避免旧回执造成假失败或重复计数；不得声称已复现此前真实游戏根因。

## 实施与验收

允许变更IPC协议状态模型/worker/native/runtime及紧邻持续时间/状态接口，前端相关类型、文案、次数口径与helper测试，版本自有元数据和必要使用说明。不得进行无关UI重构/覆盖层修复、依赖升级、游戏改动或新输入方式。

Coder先实现并用随机私有测试管道验证及时读取、延迟/不读取、读取端断开、写失败、收尾与最终回执一致性；重复有未确认仍继续、单帧无重复、精确计数，停止/到期/目标及自有Child清理紧邻回归。使用生产决策/helper与真实受控管道，不以只测硬编码文案代替关键行为。记录mock/fixture与真实游戏不同证据类型。

沿用项目内环境和离线锁定依赖。新证据位于 `build/verification/TASK-006-UI-CLEANUP/rc2/{coder,verifier,coordinator}/`，新便携包位于独立 `build/staging/TASK-006-UI-CLEANUP-rc2/`。保留rc.1全部包、清单和用户data；禁止重跑rc.1会改写产物的脚本。版本递增0.1.0-rc.2，不覆盖已交付包，不晋级release槽位。

Coder单一源码写入，稳定后提供源码清单/变化、测试及NOT RUN、EXE/ZIP/hash、脱敏交接 `rc2-coder-handoff.md`。协调者核对后才启动只读独立Verifier，复核本轮行为及紧邻回归、候选来源与洁净性；findings一次性返回用户裁定，不即时追加修复。本轮不重复全面发布审计，真实玩法/桌面交互由用户验收。

## 选型结论

沿用现有Windows命名管道，不改UDP协议。完整写入是发送口径，读取是尽力诊断。现技术目标/便携构建/项目数据边界通过；不新增依赖或全局输入。Windows文档指出断开管道可能丢弃未读数据，因此用隔离fixture验证实际关闭/短时收尾行为，不能把写成功当成可靠送达。新行为允许未确认而继续，是用户明确接受的发送语义；最终玩法仍需人工确认。
