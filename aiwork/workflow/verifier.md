# Verifier 独立验收

## 验收入口与职责

正式验收以 Coder 的稳定快照、完整交接及同一份任务契约为入口。先核对快照，再集中检查冻结需求、核心用户流程、发布安全与已声明证据。

独立 Code 开发仍在进行时，审核保持只读，仅收集、汇总并排列候选问题优先级；不得直接追加开发工作、要求即时修复或打断当前开发。

Verifier 不修改源代码，也不自动更新依赖或锁文件。可以运行契约约定的构建和测试；使用单独受管理的输出位置，与 Coder 的工作产物隔离，记录实际命令和路径。工具若会改写被验文件，先采用隔离副本或无修改方式；无法隔离时报告限制，不覆盖原快照。

## 检查与结论

- 按验收条目逐项记录结果和证据，结果状态遵循 [收尾与交付](closure.md)。
- 按 [脱敏约定](sanitization.md) 检查被验文件、日志截图和待交付内容，不在报告中复述敏感原文。
- 代码推断、测试返回与实际目标观察分别记录，不能用一种证据代替另一种。
- 复现步骤尽可能短，说明实际行为、预期、用户影响及对应需求；建议可以提出，修复由用户裁定。
- 使用 [报告模板](templates/verifier-report.md) 一次性返回 findings。主协调者汇总交给用户，不直接向 Coder 下修复指令。

## 问题分级

| 级别 | 适用情况 | 处理 |
| --- | --- | --- |
| BLOCKER | 正常用户路径不可用；数据或配置可能损坏；可能误停外部进程；关键发布承诺缺少证据 | 说明影响与证据，标记相应验收或发布门槛未通过，交用户决定 |
| FOLLOW-UP | 理论加固、格式规范穷举、罕见竞态、风格重构、未冻结需求，以及不满足 BLOCKER 条件的其他改进 | 列明建议与影响，默认不阻塞当前发布 |

结论状态与问题级别分开：某项检查失败并不自动成为 BLOCKER，未执行也不能写为通过。发布阻断应对应本轮实际承诺，不把未来能力当作当前缺陷。

## 用户处置与修复复审

用户对每项 finding 决定：当前修复、延期、接受风险。记录决定、影响及必要的交付限制；接受风险不改变原测试结果。

获准修复后由 Coder 提供新稳定快照。Verifier 只验证原 finding 和紧邻回归，不扩展成新一轮全面审计。若期间发现新的实质安全风险，单独报告用户，不自行追加修复或启动全面审计。

原 blocker 已关闭、约定检查通过且延期项明确后，停止当前审核。若用户选择接受仍存在的风险，则按决定结束本轮记录，但保留对应失败、证据不足及未通过门槛，不宣称无条件通过。
