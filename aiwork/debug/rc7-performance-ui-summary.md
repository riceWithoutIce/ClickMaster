# rc.7 性能与 UI 问题汇总

日期：2026-10-23。本文用于下一轮任务对齐，不代表本轮已开始修复。

## 当前结论

- rc.7 已通过用户人工验收，TapTapLoot 可持续响应，运行期间 loading 光标已消失。
- 当前没有证据支持性能 BLOCKER，也没有证据表明 Tauri、WebView 或现有 UI 动效本身造成持续高 CPU。
- 当前主要工作是降低技术细节对日常操作的干扰，并保留必要的诊断、日志和错误信息。
- 性能候选需要与后续 UI 调整一起冻结范围后再开发，不直接改变 IPC 保护语义。

## 性能问题与候选

| 编号 | 优先级 | 状态 | 内容 | 后续方向 |
| --- | --- | --- | --- | --- |
| PERF-R7-01 | 较高 | 待测 | 持久 IPC 每帧仍通过状态 JSON 文件发布回执，父进程约每 1ms 读取状态文件 | 在保持序号、停止、身份和清理保护的前提下，评估内存通知或更轻量的受控回执通道 |
| PERF-R7-02 | 较高 | 待测 | IPC 每帧写入前仍执行进程快照和窗口枚举，完整唯一性核验随帧频率增加 | 先记录校验耗时和调用次数，再评估相同安全语义下的缓存或分层校验 |
| PERF-R7-03 | 中 | 待测 | 消息模式约每10ms调度，并在等待下一次操作前重复验证绑定和接收窗口 | 区分等待期间检查与实际发送边界检查，保留目标失效保护 |
| PERF-R7-04 | 中 | 待测 | 前端约每1.5秒轮询多组状态，后台还有单次输入、目标验证和覆盖层线程的固定唤醒 | 让事件通知承担主要更新，保留低频兜底；避免前端轮询重入和无变化刷新 |
| PERF-R7-05 | 测量限制 | 已知边界 | 持久 worker 的阶段统计可能跨越性能采集代次，不能完整归因每一帧阶段成本 | 后续日志增加明确的 partial/unavailable 标记，再进行对比测量 |

### 性能边界

- 1ms 只用于压力测试，不代表 1kHz，也不代表目标游戏按 1ms 消费。
- 游戏约 90ms 的读取等待和有限管道缓冲是既有兼容性边界；短间隔可能积压，停止后已写入帧不能撤回。
- rc.6 的 WebView 工作集和 CPU 数据属于历史日志，不能直接作为 rc.7 当前资源结论。
- 以上候选均未在本轮重新 profile，不能按代码阅读结果宣称具体热点排名或优化收益。

## UI 问题与已对齐方向

| 编号 | 当前问题 | 已对齐方向 |
| --- | --- | --- |
| UI-R7-01 | 导航栏存在展开状态，增加了不必要的视觉层级 | 固定窄图标导航，不提供展开/收起状态；通过悬停提示识别页面 |
| UI-R7-02 | 底部运行信息、状态和按钮分散，footer 占用空间较大 | 合并为一条紧凑操作栏，集中显示运行状态、时长、次数、执行一次、开始和停止 |
| UI-R7-03 | 运行中、待命等状态颜色区分不足 | 使用文字加颜色共同表达：待命灰、准备蓝、运行绿、停止中橙、失败红 |
| UI-R7-04 | 目标窗口展示了较多开发和调试信息 | 日常只保留搜索、后台窗口开关、窗口选择、绑定状态；PID、窗口类名、接收窗口和分辨率移入详情 |
| UI-R7-05 | 诊断内容对普通用户过于常驻 | 诊断入口移入“更多”菜单或按需对话框，不删除必要内容 |
| UI-R7-06 | 错误和成功状态与技术字段混在一起 | 日常显示简短可行动提示；详细阶段、回执和错误码放入诊断详情 |

## 诊断信息保留范围

诊断入口仍需包含：

- 当前阶段、最近一次错误和停止原因；
- 目标失效、连接断开和清理失败原因；
- IPC 连接、单帧写入和读取诊断状态；
- 鼠标按下/释放投递结果；
- 已发送次数、执行时长和当前会话摘要；
- 性能日志状态及项目内日志目录入口。

用户日常界面只展示简短错误，例如“目标连接已断开，执行已停止”；完整记录仍可从诊断信息查看。日志继续遵循项目内数据目录和脱敏约定。

## 下一轮建议范围

下一轮可以拆成两个互相衔接的部分：

1. **UI 用户化整理**：固定图标导航、精简目标窗口、合并 footer、状态颜色、诊断抽屉/对话框和错误分层。
2. **性能测量与窄优化**：先补可比的待命/运行日志和 IPC 阶段计数，再决定是否替换文件回执或降低重复核验成本。

在用户补充完 UI 体验反馈前，不冻结具体 CSS、组件结构或性能实现方案；不自动开始 Coder、Verifier、构建、提交或发布。
