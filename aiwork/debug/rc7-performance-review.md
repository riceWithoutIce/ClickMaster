## PERF-R7-01：控制回执仍走文件热路径

证据：`src-tauri/src/ipc_worker.rs:75` 的 report 以 `fs::write(status.next)` 和 rename 发布；`send_persistent_frame` 在 writing 与 completed 各发布一次，见 `src-tauri/src/ipc_worker.rs:157`。`src-tauri/src/ipc_runtime.rs:398` 的 wait 每轮读取并反序列化 status.json，未结束则 sleep 1ms，见同文件 415、467 行。

这条路径即使性能采集关闭也运行。实际文件 API 次数随帧速率和等待时间增加，涉及序列化、文件打开、写入与目录元数据操作，并可能受安全软件或磁盘环境影响。它不是每帧永久新增日志文件；现有实现复用状态文件，也没有证据显示其已造成 SSD 物理写入量或当前 UI 卡顿。

现有独立 fixture 的 1ms 配置实际平均 3.485ms，包含这类回执等待，但不包含真实游戏身份核验与完整 UI，不能把差值全部归因于磁盘。后续应固定帧数、接收器与保护条件，比较控制回执的 CPU、API 次数和实际间隔，再决定是否开发替代路径。

## PERF-R7-02：完整 IPC 核验仍随帧频率增长

证据：持久 worker 在每条命令写入前调用 `lease.validate_for_send()`，见 `src-tauri/src/ipc_worker.rs:342`；该方法依次执行 fast check、unique_process 与 unique_window，见 `src-tauri/src/ipc_native.rs:318`。其中 unique_process 创建全系统进程快照并遍历，unique_window 调用 EnumWindows，见同文件 154、332 行。

连接和 worker 创建已被复用；这里没有每帧重复 EXE/程序集哈希。剩余的全系统枚举仍属于逐帧成本，因此极短间隔下可能成为下一阶段限制。其当前 CPU 占比未测，不能按旧 rc.6 数据推算。

唯一性与实际客户端写前核验属于既有保护。任何缓存或检查降频都需要先对齐如何保持保护语义，不能为追求吞吐直接删除。优先减少核验内部重复工作或在相同语义下取证。

## PERF-R7-03：消息模式等待阶段仍高频完整查询

证据：`src-tauri/src/input_runtime.rs:91` 按约 10ms 运行调度；`src-tauri/src/input.rs:390` 的 tick_inner 在判断 now < due 前先执行 adapter.valid，等待阶段也会调用。`src-tauri/src/input_native.rs:22` 的 valid 验证目标和路由；`src-tauri/src/routing_native.rs:47` 又分别 inspect root 和 receiver。

当接收窗口就是绑定窗口时，一轮 valid 通常包含三次同一窗口 inspect。每次 inspect 会 OpenProcess、GetProcessTimes、QueryFullProcessImageNameW，并读取窗口信息，见 `src-tauri/src/windows_query.rs:236`。这意味着即便配置数秒一次，消息模式仍可能约每秒执行数百次这类检查；此为代码调用频率估计，不是实测 API 计数。

此问题影响消息模式，不能解释成 rc.7 IPC 当前体验回退。消息模式还保留约 50ms 按下/释放配对和 10ms tick；1ms 参数也不等于实际 1ms 完整操作，这属于现有语义，非本轮发现的故障。

## PERF-R7-04：待命与隐藏界面的固定周期工作

证据：`src/App.vue:170` 的 pollBinding 依次请求性能、绑定、覆盖层、输入、通道五个状态，`src/App.vue:257` 每 1500ms 触发一次；它没有按页面、诊断折叠或托盘状态暂停，也没有单轮在途标记。后端已有状态事件；前端接受相同 revision 并重新替换对象。

后台 `single-input` 线程待命时仍约每 10ms 检查锁和复制状态，见 `src-tauri/src/input_runtime.rs:20`；关闭的覆盖层线程仍约每 80ms 唤醒并 pump，见 `src-tauri/src/overlay_runtime.rs:86`。另有每秒绑定/路由验证，见 `src-tauri/src/lib.rs:955`。这些是固定唤醒与分配成本，不是忙等待或已证明的高 CPU。

若某轮前端状态查询超过 1.5 秒，setInterval 可启动下一轮，形成重叠请求；这属于条件性放大风险，尚未复现。正常状态查询没有每轮重扫目标列表，通道兼容性也已按绑定 epoch 缓存，不能将它描述为每 1.5 秒完整版本哈希。

后续可和 UI 反馈统一整理：保留必要事件/低频兜底、避免重复对象更新、同一轮查询在途时不重入、隐藏时减少展示更新。后台 F8/停止/目标失效监控不能依赖 WebView 定时器。

## PERF-R7-05：持久连接后的阶段统计覆盖不足

证据：`src-tauri/src/ipc_worker.rs:295` 仅在 worker 授权时决定是否采集及使用哪个 performance_epoch；`src-tauri/src/ipc_runtime.rs:489` 在持久会话 shutdown 时才 merge_worker。`src-tauri/src/performance.rs:500` 仅合并当前非零代次，60 秒结束时在同文件 989 行关闭 ACTIVE。

因此，先开始 IPC 再开始采集时，worker 的逐阶段指标可能未开启或属于旧代次；先采集再开始 IPC、但 IPC 超过采集结束仍未停止时，当前日志可能没有收到最终阶段合并。主程序/worker CPU、内存和发送量的独立采样仍可用，不应将整个日志判为无效。

TASK-011 Verifier 已披露这个覆盖限制。本轮将它列为后续测量前提，不升级为新功能 blocker。若需要定位以上热路径，应先定义采集窗口内阶段增量与明确的不可用/部分状态，不重新启用客户端读取确认阻断。

## 已知边界和排除

- 游戏静态消费者存在约 90ms 读取等待，见 `aiwork/debug/taptaploot-input-mechanism-analysis.md:56`。极短间隔持续发送可能填满有限缓冲并进入写等待/超时，停止不能撤回已写帧。Verifier 未读客户端 fixture 已证明 1024 帧后约 2.013 秒超时；不能据此断言真实游戏目前发生同样故障。该边界已公开，不作为新 finding，不擅自恢复读取确认阻断或改协议。
- 旧 rc.6 关联 WebView 环境工作集约 366MiB，归属可能共享；其可归属整机平均 CPU 约 0.624%。只能说明那轮日志，不能作为 rc.7 当前资源值、泄漏或性能恢复证据。rc.7 资源是否满足用户的轻量目标仍可用新日志确认。
- 前端构建 JS 约 104KB、CSS 约 9KB、图标约 1KB；CSS 未发现无限循环动画。现有证据不足以把较高内存归因于 UI 动效或大前端依赖，也没有理由因本轮 review 更换 Tauri。
- 专用 IPC 开始路径会重复读取/哈希支持程序集，见 `src-tauri/src/lib.rs:90`、211 行，worker 也在 Lease::open 时核验；属于每次启动成本，不是持续逐帧成本，暂列低优先观察，不扩成独立修复。
